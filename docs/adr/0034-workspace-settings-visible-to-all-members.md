# 0034. Экран настроек пространства доступен ВСЕМ участникам; ролевое ограничение живёт внутри экрана

- Дата: 2026-08-03
- Статус: accepted
- Контекст находки: `docs/audit/roadmap.md` §7.39 (F44)

## Контекст

Кнопка «Покинуть пространство» находится во вкладке «Участники» экрана `/workspace-settings`. Единственная ссылка на этот экран — пункт «Настройки пространства» в меню переключателя пространств (`src/components/WorkspaceSwitcher.tsx`) — была обёрнута гейтом `{canEdit && …}` с комментарием «только editor+ (viewer не видит)».

Для роли `viewer` хук `useCanEdit()` возвращает `false`, поэтому наблюдатель не имел вообще никакого входа на экран настроек пространства, а вместе с ним и способа выйти из пространства: он оказывался заперт до тех пор, пока владелец не удалит его вручную.

Серверная сторона при этом полностью исправна — политики прод-БД (прочитаны напрямую 03.08.2026):

- `sync_workspace_members_select_ws_role` — USING `has_workspace_role(workspace_id, auth.uid(), 'viewer') OR user_id = auth.uid() OR is_workspace_bootstrap(...)`: наблюдатель имеет право читать список участников своего пространства;
- `sync_workspace_members_self_leave_update` — USING/CHECK `user_id = auth.uid() AND role <> 'owner'` (+ `deleted_at IS NOT NULL` в CHECK): гашение своей строки разрешено ЛЮБОМУ не-владельцу, то есть и наблюдателю (ср. ADR 0033, где этот же путь используется для push'а `op='delete'`).

То есть ограничение было чисто клиентским и не отражало ни модель прав на сервере, ни контракт самого экрана.

## Решение

Ссылка «Настройки пространства» показывается **всем участникам пространства**, включая `viewer`. Гейт `canEdit` в `WorkspaceSwitcher` снят вместе с ставшим ненужным вызовом `useCanEdit()`.

Права по ролям остаются там, где они уже реализованы — **внутри экрана**, а не на входе в него:

- переименование и удаление пространства — только `owner`;
- справочники статусов, тегов и дедлайнов (`StatusesSection`/`TagsSection` из `src/pages/Settings.tsx`, `DeadlinesSection`) гасятся хуком `useCanManageWorkspace()`;
- `MembersTab` по своему контракту показывает `editor`/`viewer` только список участников и кнопку «Покинуть пространство» (кнопка рисуется при `!isOwner && myMembership`); приглашение и удаление участников — только у владельца;
- вкладка «Участники» доступна только для общего пространства (`isShared`).

Дополнительно в `WorkspaceSwitcher` добавлен якорь `data-onboarding="workspace-switcher"`, чтобы шаг «Пространства» приветственного тура подсвечивал сам переключатель (см. §7.39).

## Альтернативы (отклонены)

1. **Отдельный урезанный экран или модалка «Выйти из пространства» для viewer'а.** Это второй слой поверх уже существующего ролевого экрана — противоречит принципу «убирать сломанный слой, а не строить костыль поверх» и создаёт вторую точку правды о том, что видит наблюдатель.
2. **Показывать пункт меню «Покинуть пространство» прямо в переключателе.** Дублирует действие, которое уже есть на экране участников, и разводит выход из пространства по двум местам с разными подтверждениями.
3. **Оставить как есть и разрешать выход только владельцу через удаление участника.** Прямо противоречит серверной политике `sync_workspace_members_self_leave_update`, которая специально написана под самостоятельный выход не-владельца.

## Последствия

- Наблюдатель видит экран настроек пространства в read-only виде и может выйти из пространства сам; путь выхода тот же, что у editor'а, — значит работает и фикс push'а из ADR 0033.
- Появляется инвариант, который нужно держать: **ролевые ограничения экрана `/workspace-settings` живут внутри экрана**. Любая новая секция там обязана сама гаситься по роли (`useCanManageWorkspace()` / `isOwner`), а не рассчитывать на то, что не-editor туда не дойдёт.
- Схема БД, RLS, логика членства и приглашений (ADR 0008/0009/0011) и sync-цикл не затронуты; миграций нет.
- Верификация: `src/components/WorkspaceSwitcher.test.tsx` — viewer видит ссылку и её `href`, владелец видит её по-прежнему, якорь онбординга присутствует. Полный прогон 03.08.2026: 89 файлов / 742 теста, `tsc --noEmit` чист.
