# ADR 0032. Явный цвет аватара (`profiles.avatar_color`) и редизайн «Настройки → Аккаунт» (F41)

- **Статус:** accepted
- **Дата:** 03.08.2026
- **Ветка:** `feat/member-profiles-account-redesign`
- **Контекст находок:** roadmap §7.36 (F41)
- **Связанные решения:** Post-v1.0.2 (профильные поля `nickname`/`avatar_variant`/`bio`), ADR 0031 (публичные профили участников — тот же PR), ADR 0002 (гранты для RPC)

## Контекст

Пункт 6 брифа: перестроить блок «Настройки → Аккаунт» и дать пользователю **явный** цвет аватара.

Как было:

1. `ProfileBlock` шёл ниже блока с email/«Зарегистрирован»/«Последний вход»; ник, «о себе», публичный ID и сетка из 8 форм аватара лежали одним вертикальным потоком, аватар как таковой (в человеческом размере) не показывался.
2. Цвет глифа брался из CSS-переменной темы: `Avatar` рисовался классами `text-accent` + `bg-surface-alt`. Значит цвет **менялся вместе с темой приложения** и не был свойством пользователя. Побочное следствие для общих пространств: даже когда ник и форма аватара известны (онлайн-участники через presence), цвет у всех был один — акцент **моей** темы, из-за чего аватары выглядели одинаковыми.

Требование пользователя по цвету: «чтобы у всех отображался тот цвет, который пользователь себе сам задал», и произвольный выбор (пикер), а не палитра из N вариантов.

## Решение

### 1. Цвет — колонка профиля, а не производная темы (миграция 0042)

```sql
alter table public.profiles add column if not exists avatar_color text;
alter table public.profiles add constraint profiles_avatar_color_format
  check (avatar_color is null or avatar_color ~* '^#[0-9a-f]{6}$');
```

- `NULL` — «цвет не задан», обратная совместимость: старые профили и старые сборки клиента продолжают рисовать аватар акцентом темы, как раньше;
- формат проверяется **на сервере** (CHECK), а не только в клиентской валидации;
- отдельной таблицы/справочника нет: цвет — такая же косметика профиля, как `avatar_variant`, и живёт рядом с ним.

Колонка отдаётся наружу двумя путями: своим профилем (`src/lib/profile.ts`, `PROFILE_COLUMNS`) и публичной RPC `get_workspace_member_profiles` (ADR 0031) — поэтому цвет одинаков у всех, кто смотрит на участника.

### 2. `Avatar` — цвет inline, без `color-mix`

`Avatar({ variant, color, size })`:

- `color === null` → прежнее поведение: классы `text-accent` / `bg-surface-alt` (тема);
- валидный `#rrggbb` → inline `color` + `backgroundColor` из `avatarTint(color, 0.14)`.

`avatarTint` считает `rgba(...)` руками, **без CSS-функции `color-mix`**: клиент работает в системном WebView (Tauri, в том числе WebView2/WebKitGTK старых сборок), и полагаться на поддержку `color-mix` в проде нельзя. Невалидное значение цвета игнорируется — падаем на тему, а не рисуем сломанный аватар.

### 3. Выбор аватара — модальное окно (`AvatarEditorModal`)

Требование брифа «выбор/смену аватарки — во всплывающем окне». В модалке: превью **на светлой и на тёмной подложке** одновременно (пользователь сам видит читаемость цвета в обеих темах), сетка форм, системный `input type="color"`, hex-поле с валидацией и подсказкой «Формат: #rrggbb», 10 быстрых свотчей. Значения уезжают наружу только по «Готово»; «Отмена»/Esc не меняют ничего, повторное открытие сбрасывает черновик. Сохранение в БД — по кнопке «Сохранить профиль» блока «Профиль» (одна точка записи, как раньше).

### 4. Порядок блоков в «Аккаунте»

Блок «Профиль» перенесён **выше** блока с email: внутри него ник + поле ввода слева, текущая аватарка (64px) и кнопка «Изменить» справа на том же уровне; ниже «О себе» со счётчиком, ниже «Ваш ID» с копированием. Под «Профилем» — прежний блок email / «Зарегистрирован» / «Последний вход» (не переписывался).

### 5. Presence передаёт цвет

`PresenceMeta`/`PresenceMember` дополнены `avatar_color` / `avatarColor`. Поле **опционально** в meta: клиент прошлой версии его не пришлёт, и такой участник просто отобразится без явного цвета. Это осознанный компромисс вместо версионирования канала presence.

## Альтернативы

- **Фиксированная палитра из 8–12 цветов вместо пикера.** Отклонено: пользователь явно попросил «любой цвет (пикер)». Свотчи оставлены как быстрый выбор поверх пикера.
- **Хранить цвет только локально (`localStorage`).** Отклонено: тогда участники общих пространств видели бы не тот цвет, который человек себе задал, — то есть исходная жалоба не закрывалась бы.
- **Выводить цвет из ника/uuid (хеш → HSL).** Отклонено: аватары стали бы разными, но «не своими» — выбор всё равно не принадлежал бы пользователю.
- **`color-mix(in srgb, var(--x) 14%, transparent)` для подложки.** Отклонено: неизвестная поддержка в целевых системных WebView; ручной `rgba()` даёт тот же результат предсказуемо.
- **Оставить выбор формы инлайн, в модалку вынести только цвет.** Отклонено: два разных места для одной сущности; бриф просил именно окно.

## Последствия

- Цвет аватара перестал зависеть от темы: сменив тему, пользователь увидит свой аватар в том же цвете. Это **намеренное** изменение внешнего вида для тех, кто цвет задал; у профилей с `avatar_color = NULL` поведение прежнее.
- Требуется применить миграцию `0042` на прод **до** выпуска сборки: клиент запрашивает колонку в `PROFILE_COLUMNS`, и без неё чтение профиля упало бы.
