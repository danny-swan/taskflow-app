# ADR 0029. Последовательная очередь нативных записей + слот free-аккаунта прямо перед выходом (F37)

- **Статус:** accepted
- **Дата:** 03.08.2026
- **Ветка:** `fix/f37-logout-write-flush`
- **Контекст находки:** roadmap §7.32 (F37)
- **Связанные решения:** ADR 0014 (локальный слот free-аккаунта, F21), ADR 0023 (auto-restore из файлового снимка с рестартом, F30), ADR 0028 (F36 — явный `workspace_id` при сиде), Fix 5 (`sync/logoutFlush.ts` — досыл outbox перед logout для Pro/Trial)

## Контекст

Пользователь сообщил (03.08.2026, после ручного подтверждения F36): «если создать задачу на free-аккаунте и быстро выйти из аккаунта, потом зайти в другой и вернуться — задача может пропасть, видимо не успела сохраниться». Наблюдалось на аккаунте `e46d9d68-…` (`test4`), пространство «Мои задачи».

В присланных `data.db` + `data-4.db-wal` + `taskflow-5.log` **следов конкретной пропавшей строки нет** — и не может быть: `applyBackup(..., 'replace')` при восстановлении слота стирает таблицы, а сам слот живёт в `localStorage` webview и в выгрузку не попадает. Поэтому корень доказан не «пропавшей строкой», а двумя измеримыми фактами: (1) содержимым лога (когда именно писался слот) и (2) кодом путей записи. Оба сходятся на одном классе проблемы, что и делает симптом воспроизводимым.

### Факт 1 — слот free-аккаунта при обычном выходе не писался вовсе

`localStorage['taskflow.localstore.v1.<uid>']` (ADR 0014) обновлялся только:

- `useLocalAccountAutosave` — **через 30 с тишины** после мутации (`AUTOSAVE_DEBOUNCE_MS = 30_000`);
- `beforeunload` / `visibilitychange` — закрытие или сворачивание окна;
- `AccountSwitchGate` (free-ветка) — при входе в **другой** аккаунт, слот уходящего.

`Settings.handleSignOut` слот не писал: там был только `flushOutboxBeforeLogout` (Fix 5), а он по своему инварианту работает **исключительно** для Pro/Trial (`if (!isProOrTrial(ent)) return`). Для free выход был «пустым» — данные полагались на дебаунс. В логе это видно прямо: последние записи слота идут через 30–48 с после мутаций (`12:43:59 saved slot for e46d9d68 (tasks=3)` — через 48 с после предыдущего восстановления), а после последнего действия сессии записи слота нет вообще.

Пока приложение живо, это ещё не потеря: Gate при входе в следующий аккаунт читает то же sql.js-зеркало и успевает сохранить слот. Но если между выходом и возвратом процесс перезапускался — а в этой сессии рестарты были и штатные (`app start` в 12:39:47, 12:40:03, 12:43:25, часть из них — рестарт после `restoreSnapshot`, ADR 0023), — зеркало умирало вместе с процессом, и задача, созданная за секунды до выхода, оставалась только в нативной `data.db`.

### Факт 2 — записи в нативную SQLite шли независимыми промисами, без порядка и без точки ожидания

`db.run()` в Tauri (db.ts ≈1543) обязан быть синхронным (на этом построен весь стор), поэтому SQL применялся к зеркалу сразу, а в нативную базу уходил так:

```ts
getTauriDb().then((d: any) => d.execute(sql, params)).catch(console.warn);
```

Каждая команда — **отдельный** промис. Отсюда два следствия:

1. **Порядок не гарантирован.** Для пачки команд (`clearUserData()` → `applyBackup()` слота, восстановление, реконсиль) более медленная ранняя команда могла примениться позже более быстрой поздней. В пределе `DELETE` ложился **после** `INSERT`: в зеркале строки нет, в файле есть (или наоборот — строка есть в зеркале, но её `INSERT` не доехал, а `DELETE` доехал). Тот же механизм fire-and-forget уже был корнем F18 (ADR 0012), F31 и F36 (ADR 0028) — там он проявлялся как «зеркало и файл разошлись».
2. **Ждать было нечего.** Ни выход из аккаунта, ни `createSnapshot`, ни `restoreSnapshot` (подмена файла `data.db` через Rust) не могли дождаться незавершённых записей. Комментарий в `snapshots.ts` честно фиксировал: «run() пишет в Tauri DB fire-and-forget… небольшой лаг возможен» — но сделать с этим лагом было нечего.

## Решение

Два точечных изменения; новых слоёв и фоновых механизмов не добавляем.

### 1. Одна последовательная очередь записей + `flushNativeWrites()`

`db.ts`: вместо независимого промиса на команду — цепочка.

```ts
let nativeWriteChain: Promise<void> = Promise.resolve();

function enqueueNativeWrite(sql: string, params: any[]): void {
  nativeWriteChain = nativeWriteChain.then(async () => {
    try {
      const d = await getTauriDb();
      await d.execute(sql, params);
    } catch (e) {
      console.warn('[db] native write failed:', e);
    }
  });
}

export async function flushNativeWrites(): Promise<void> {
  if (!IS_TAURI) return;
  await nativeWriteChain;
  await nativeWriteChain; // за время ожидания в цепочку могли добавиться звенья
}
```

- **Контракт `run()` не изменился**: он по-прежнему синхронный и по-прежнему не ждёт нативную запись. Меняется только то, что записи доезжают до файла **в порядке вызова**.
- Ошибка одного звена ловится внутри и не рвёт цепочку — иначе одна неудачная запись остановила бы все последующие.
- В web-режиме `flushNativeWrites()` — no-op (нативной базы нет).

Точки ожидания (там, где состояние в памяти вот-вот будет потеряно или файл будет подменён):

- `snapshots.createSnapshot()` (Tauri-ветка) — перед `invoke('snapshot_db')`: снимок теперь гарантированно содержит последние мутации;
- `snapshots.restoreSnapshot()` (Tauri-ветка) — перед `invoke('restore_snapshot')`: команды «в полёте» не применятся к уже заменённому файлу и не потеряются вместе с ним;
- `logoutLocalSlot.saveFreeSlotBeforeLogout()` — перед выходом из аккаунта.

### 2. Слот free-аккаунта пишется прямо перед обычным выходом

Новый маленький модуль `src/lib/logoutLocalSlot.ts` — симметричный аналог `sync/logoutFlush.ts`, только для локального «псевдо-облака»:

```ts
export async function saveFreeSlotBeforeLogout(userId, email): Promise<LogoutSlotResult>
```

- no-op, если `getBoundUserId() !== userId` (мы в середине смены аккаунта — писать чужое состояние нельзя);
- no-op для Pro/Trial/Lifetime — **инвариант ADR 0014** сохранён (слот принадлежит free; лишний слот мог бы «воскреснуть» при даунгрейде);
- иначе `saveLocalAccountData(userId)` + `flushNativeWrites()`;
- никогда не бросает: выход не блокируется ни при какой ошибке (тот же принцип, что у Fix 5).

Вызов — в `Settings.handleSignOut`, перед `flushOutboxBeforeLogout` и `signOut()`.

## Альтернативы

- **Сократить дебаунс автосейва (30 с → 2–3 с).** Отклонено: не решает проблему (окно потери остаётся, просто уже), но заметно повышает частоту сериализации всей базы в `localStorage` — тот самый «костыль поверх», а не устранение причины.
- **Сделать `db.run()` асинхронным (await нативной записи).** Отклонено: это переписывание всего стора и всех синхронных вызывающих мест — несоразмерный риск ради редкого сценария. Очередь даёт нужную гарантию порядка без смены контракта.
- **Писать слот на каждую мутацию.** Отклонено: полная сериализация БД в `localStorage` на каждое нажатие — деградация UI и риск переполнения носителя.
- **Блокировать выход до подтверждения записи (спиннер/таймаут).** Отклонено как поведение: выход обязан пройти всегда. Ожидание очереди — миллисекунды на локальной SQLite, и оно уже внутри `saveFreeSlotBeforeLogout`, который не может провалить выход.

## Последствия

- Записи в файл упорядочены — устранён общий корень целого класса расхождений «зеркало ≠ файл» (F18/F31/F36 лечили его частные проявления).
- Снимки и `restoreSnapshot` больше не гоняются с записями «в полёте».
- Выход из free-аккаунта фиксирует состояние сразу, а не через 30 с.
- Цена: записи применяются строго последовательно, то есть медленная команда задерживает следующие. Для локальной SQLite это единицы миллисекунд; выигрыш в консистентности несоизмеримо больше.
- Не затронуты: схема БД и миграции (их нет), логика членства/инвайтов (ADR 0008/0009/0011), облачный путь Pro/Trial, F36 (ADR 0028), формат слота и снимков.

## Верификация

- Новый `src/lib/db.nativeWriteQueue.test.ts` (4 кейса, реальный Tauri-путь `db.ts` поверх sql.js-адаптера с искусственной задержкой): порядок «медленный INSERT → быстрый DELETE» сохраняется; `flushNativeWrites()` действительно ждёт (до него строки в нативной базе нет, после — есть); ошибка одного звена не рвёт очередь; в web — no-op. **Проверено, что без фикса 2 из 4 кейсов падают** — регресс валиден, а не декоративен.
- Новый `src/lib/logoutLocalSlot.test.ts` (6 кейсов): free → слот + flush; Pro/Trial → no-op; чужой `bound_user_id` → no-op; привязки нет → no-op; слот не записался → `saved=false` + warn; исключение внутри не пробрасывается.
- Полный прогон `vitest run`: **81 файл / 668 тестов — все зелёные**; `tsc --noEmit` чист. Сборка — только в CI (локально OOM).
- Ручная проверка пользователем — до закрытия находки: создать задачу и в течение 2–3 с выйти из аккаунта, войти в другой, вернуться; задача должна быть на месте. Повторить с перезапуском приложения между выходом и возвратом.
