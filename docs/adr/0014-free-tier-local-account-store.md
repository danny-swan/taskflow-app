# 0014. Локальное per-account хранилище для free-аккаунтов

- Статус: accepted
- Дата: 2026-08-02
- Связано: находка F21 (эпик «Пространства», roadmap §7.22), ветка `feat/workspaces`,
  `src/components/AccountSwitchGate.tsx` (free-ветка, введена в dev.6.10.3),
  [ADR 0010](0010-sqlite-corruption-auto-recovery.md) (тот же класс «чисто
  клиентский фикс поверх локальной SQLite»); **без серверных миграций**, схема
  `docs/architecture/erd.md` не меняется.

## Контекст

Free-план не имеет облачной синхронизации: гейт в `src/lib/sync/index.ts`
(~296-315) при `!isProOrTrial(ent)` завершает цикл статусом `paywalled` — ни
`pullAll`, ни `pushAll` не выполняются, наверх поднимается только локальный
bootstrap. Одновременно локальная SQLite — **одна на устройство, а не на
аккаунт** (единственный файл `data.db` в Tauri / единственный блоб
`taskflow.sqlite.v1` в вебе).

Пересечение этих двух фактов и даёт потерю данных. При входе под другим
аккаунтом `AccountSwitchGate` (free-ветка, строки 172-207 до этого фикса)
делает локальную перепривязку без сети:

```
createSnapshot('before_account_switch') → db.clearUserData() →
setBoundUserId(new) → reconcilePersonalWorkspace(new) →
ensureSeededIfEmpty() → ensureWelcomeTaskIfNeeded(new)
```

Данные уходящего free-аккаунта попадают **только** в общий снимок
(`src/lib/snapshots.ts`), у которого две особенности: он ротируется (`MAX_SNAPSHOTS
= 5`, старые тихо удаляются) и восстанавливается исключительно вручную из
Настройки → Синхронизация. Автоматического обратного пути нет — поэтому при
возврате на тот же free-аккаунт пользователь видит пустую доску с одной
welcome-задачей.

Воспроизведение (подтверждено пользователем): аккаунт `test3` (free) → создал
задачи → переключился на основной аккаунт (локальная база перезаписана) →
вернулся на `test3` → пусто.

Для Pro/Trial/Lifetime проблемы нет: у них источник истины — облако, и та же
смена аккаунта проходит через модалку с тремя вариантами (cloud/local/merge),
каждый из которых дёргает `syncNow()`.

## Решение

Дать free-аккаунтам **локальный аналог облака** — постоянный слот-слепок БД на
каждый `user_id`, который подставляется автоматически при входе и обновляется
при уходе.

**1. Модуль `src/lib/localAccountStore.ts` (новый).**

- `saveLocalAccountData(userId)` — `db.buildBackup({tasks, tags, statuses})`
  (шаблоны `task_templates` попадают в дамп автоматически) → JSON → слот.
- `loadLocalAccountData(userId)` — слот → `db.applyBackup(payload, 'replace')`
  → `true`; если слота нет/он пуст/битый — `false` без исключений.
- `hasLocalAccountData(userId)` — есть ли непустой слот.

**Носитель — `localStorage['taskflow.localstore.v1.<userId>']` в обоих режимах.**
В вебе это единственный вариант (так же хранится полезная нагрузка web-снимков).
В Tauri рассматривался файл в app-data-dir, но `@tauri-apps/plugin-fs` в проект
не подключён (нет ни в `package.json`, ни в `src-tauri/Cargo.toml`), а заводить
новую Rust-команду ради одного JSON-слота — несоразмерно: снимки используют
Rust (`snapshot_db`) только потому, что копируют бинарный файл БД и требуют
перезапуска приложения. `localStorage` в webview персистентен между запусками
(WebView2/WKWebView держат его в профиле app-data), а формат `BackupPayload`
кросс-режимный — восстановление работает без рестарта, в отличие от
`restoreSnapshot` в Tauri.

**Слот — не снимок.** Он вне ротации `MAX_SNAPSHOTS`, ровно один на аккаунт
(каждый save перезаписывает предыдущий) и не показывается в UI снимков.

**2. Free-ветка `AccountSwitchGate.tsx`.** Новый порядок:

```
saveLocalAccountData(check.boundUserId)   ← НОВОЕ: слот УХОДЯЩЕГО аккаунта
createSnapshot('before_account_switch')   ← оставлен как страховка
db.clearUserData()
setBoundUserId(sessionUserId)
reconcilePersonalWorkspace(sessionUserId)
restored = await loadLocalAccountData(sessionUserId)   ← НОВОЕ
если !restored → ensureSeededIfEmpty() + ensureWelcomeTaskIfNeeded()
reloadAccountBinding() + refresh() + тост (текст зависит от restored)
```

Два порядковых требования, оба существенные:

- `saveLocalAccountData` берёт **старый** `boundUserId` (из `checkAccountBinding`,
  до `setBoundUserId`) и вызывается **до** `clearUserData()` — иначе сохранять
  будет нечего.
- `loadLocalAccountData` идёт **после** `reconcilePersonalWorkspace`: `applyBackup`
  штампует восстановленные строки `current_workspace_id` из `settings`
  (`db.ts`, ~1640-1646), а этот указатель на personal-ws нового аккаунта
  выставляет как раз реконсиль. При обратном порядке строки уехали бы в
  `ws_local`/чужой ws и выпали из ws-scoped выборок UI.

**3. Автосейв активной free-сессии — `src/lib/useLocalAccountAutosave.ts`
(новый хук, монтируется в `App.tsx` после `ready`).** Подписка на `useStore`
(без ререндера App), дебаунс 30 с по изменению `tasks`/`tags`/`statuses`, плюс
немедленная запись на `beforeunload` и `visibilitychange → hidden`. Нужен
потому, что уйти с аккаунта можно и мимо гейта (краш, убитый процесс). Гейт
внутри хука: план не Pro/Trial/Lifetime **и** `getBoundUserId() === userId`
(вторая проверка отсекает запись в момент незавершённой смены аккаунта).

## Инварианты

1. **Только free.** Весь новый код вызывается из free-ветки
   `if (!isProOrTrial(ent))` и из автосейв-хука под тем же гейтом. Ветка
   Pro/Trial/Lifetime (`setOpen(true)` → модалка cloud/local/merge → `syncNow`)
   не изменена ни на строку.
2. **Pro никогда не читает слот.** Источник истины для Pro — облако. Даже если
   слот остался с free-времён, он не читается.
3. **Free → Pro:** при следующем входе аккаунт попадает в pro-ветку, слот
   игнорируется. Мёртвый слот безопасен (лежит в localStorage до переустановки).
4. **Изоляция per-`user_id`.** Ключ содержит `user_id`; N free-аккаунтов на
   устройстве не видят слоты друг друга.
5. **Пустой дамп не затирает живой слот.** Дамп без единой строки — это
   транзитное состояние сразу после `clearUserData()`; запись такого дампа
   уничтожила бы данные аккаунта, поэтому `saveLocalAccountData` возвращает
   `false` и слот не трогает.
6. **Серверных миграций нет**, схема БД не менялась.

## Альтернативы — рассмотрены и отклонены

- **A) Namespace по `user_id` внутри схемы SQLite** (колонка-владелец на всех
  таблицах или отдельные наборы таблиц на аккаунт). Инвазивно: затрагивает
  каждый запрос UI и все sync-мапперы, требует миграции локальной схемы и
  сверки с серверной (`erd.md`), риск регрессий несоизмерим с проблемой,
  которая касается только free-плана.
- **B) Отдельный файл БД на аккаунт** (`data.<userId>.db` в Tauri). Требует
  переключения соединения `@tauri-apps/plugin-sql` на лету и Rust-команд для
  управления файлами; в вебе аналога нет (один блоб в localStorage) — режимы
  разъезжаются. Плюс перезапуск при переключении, как у `restoreSnapshot`.
- **C) Отменить ротацию снимков и восстанавливать из них автоматически.**
  Снимок — универсальная страховка «перед разрушающим действием», а не
  хранилище аккаунта: он один на устройство, ротируется, в Tauri бинарный и
  требует рестарта. Привязывать к нему семантику «данные аккаунта» — смешение
  двух разных инструментов; кроме того, автоматический restore снимка в Tauri
  означал бы перезапуск приложения при каждой смене аккаунта.
- **D) Дать free-плану облачную синхронизацию.** Продуктовое решение, а не
  техническое: облако — платная фича, в этом и смысл гейта.

## Тесты

- `src/lib/localAccountStore.test.ts` (новый, 9 тестов): roundtrip
  save → has → load (`applyBackup` получает тот же payload в режиме `'replace'`);
  перезапись слота повторным save; изоляция по `userId` (слот A не виден B, у
  каждого свой payload); load без слота → `false` без вызова `applyBackup`;
  `userId=null` — no-op; пустой дамп не затирает живой слот; битый JSON в слоте
  → `false` без исключения; ошибка `applyBackup` → `false`.
- `src/components/AccountSwitchGate.test.tsx` (обновлён, +4 теста, блок «F21»):
  слот уходящего аккаунта пишется под **старым** `boundUserId` и **до**
  `clearUserData` (проверка по `invocationCallOrder`); при наличии слота нового
  аккаунта данные восстанавливаются и сев **не** выполняется, а
  `reconcilePersonalWorkspace` идёт до `loadLocalAccountData`; без слота — сев
  как раньше; в pro-ветке слот не читается и не пишется. Существующие тесты
  free/pro-веток не менялись.

## Последствия

- `applyBackup` ставит восстановленные строки в `sync_outbox` (поведение
  dev.6.10.4, нужное для Pro). У free push не выполняется, поэтому очередь
  просто копится локально; чип «pending sync» для статуса `paywalled` скрыт
  (`shouldHidePendingChip`, P2 из §7.10), так что пользователь этого не видит.
  При апгрейде free → Pro накопленная очередь уедет в облако первым же
  `syncNow()` — это желаемое поведение (данные не теряются), но объём первого
  push может быть заметным.
- Слот занимает место в localStorage (JSON-дамп, тот же порядок величины, что
  web-снимок). При переполнении хранилища `saveLocalAccountData` возвращает
  `false` и логирует warning — смена аккаунта при этом не ломается, страховкой
  остаётся снимок.
- Слоты не удаляются автоматически: аккаунт, которым больше не пользуются,
  оставляет за собой слепок до переустановки/очистки хранилища. Осознанный
  компромисс — автоудаление по «давности» рисковало бы стереть данные
  аккаунта, к которому пользователь просто редко возвращается.
- Восстановление опирается на JSON-дамп (`buildBackup`), а не на бинарную
  копию БД: как и у web-снимков, за пределами `tasks/tags/statuses/templates`
  ничего не переносится (UI-настройки, `client_id`, реестр снимков остаются
  устройства, а не аккаунта). Для free это полный набор пользовательских данных.

## Что осталось (не в этом PR)

- Явная чистка слота при «Стереть все данные» и при удалении аккаунта —
  сейчас слот переживает обе операции (по умолчанию — в пользу сохранности
  данных). Функция `deleteLocalAccountData` намеренно не добавлена, пока нет
  вызывающего.
- В Tauri автосейв опирается на `beforeunload`/`visibilitychange`; событие
  закрытия окна Tauri (`onCloseRequested`) не перехватывается — при жёстком
  закрытии окна теряются изменения последних ≤30 с (дебаунс). Отдельный
  close-хук в проекте отсутствует; заводить его ради этого не стали.
- Слот не шифруется (как и web-снимки, и сама локальная БД) — угроза «другой
  пользователь ОС читает localStorage приложения» этим фиксом не адресуется.
