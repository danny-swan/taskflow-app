# ADR 0036 — Название пространства и профиль пригласившего в карточке приглашения

- **Статус:** accepted
- **Дата:** 2026-08-05
- **Находка:** F56 (`docs/audit/roadmap.md` §7.51)
- **Миграция:** `supabase/migrations/0044_my_pending_invites_rpc.sql`
- **Связанные решения:** ADR 0031 (публичные профили участников через RPC), ADR 0002 (гранты на функции), ADR 0027 (миграции применяются вручную), `docs/architecture/wave-b-plan.md` §4.4-факт (прежнее решение — «approach 5.b»)

## Контекст

Карточка входящего приглашения в левом меню (`src/components/MyInvitesSection.tsx`) показывала нейтральный заголовок «Приглашение в общее пространство»: ни названия пространства, ни того, кто пригласил. Пользователь, получивший инвайт, не мог отличить одно приглашение от другого и не понимал, от кого оно.

Это не недоделка UI, а следствие RLS — приглашённый **ещё не участник** пространства. Проверено на проде под ролью приглашённого (`set local role authenticated` + `request.jwt.claim.sub`, всё в откатываемой транзакции):

| Запрос от лица приглашённого | Результат |
| --- | --- |
| `select name from sync_workspaces where id = <ws>` | **0 строк** — политика отдаёт пространство только его участникам |
| `select public_user_id, nickname … from profiles where id = <inviter>` | **0 строк** — на `profiles` только own-row `profiles_select_own` |
| `select * from sync_workspace_invites where target_user_id = auth.uid()` | 1 строка — читается нормально (`invites_select_ws_role`) |

То есть у клиента на руках были только идентификаторы (`workspace_id`, `inviter_user_id`), а все отображаемые поля закрыты. Именно поэтому в Wave B (PR-b-04) было выбрано «approach 5.b» — нейтральный заголовок без backend-правок. Это решение здесь пересматривается: без имени пространства и автора приглашение остаётся непонятным, а обойти RLS клиентом нельзя в принципе.

## Рассмотренные варианты

1. **Ослабить RLS на `sync_workspaces` / `profiles`** — дать приглашённому читать строку пространства и профиль пригласившего напрямую.
   Отклонено: политику пришлось бы писать «видно тем, у кого есть pending-инвайт» на двух таблицах, включая `profiles`, где own-row-изоляция — базовая гарантия. Широкая правка модели доступа ради двух подписей.
2. **Класть имя пространства и ник в саму строку приглашения** при создании (денормализация в `sync_workspace_invites`).
   Отклонено: данные протухают (переименовали пространство или сменили ник — в карточке старое), плюс это уже запись, а не чтение, и требует правки `invite_to_workspace`.
3. **Отдавать имя пространства через `accept_invite`** — то есть не показывать до принятия.
   Отклонено: не решает задачу, решение о принятии как раз и принимается по этой карточке.
4. **Оставить как есть (approach 5.b)** и объяснить пользователю ограничение.
   Отклонено: пользователь явно попросил показать эту информацию, а ограничение снимается штатным для проекта способом (см. ниже).
5. **Отдельная RPC на каждое поле** (имя ws + профиль по id).
   Отклонено: два круга к серверу на каждую карточку и второй гейт, который надо отдельно доказывать; список приглашений и так один запрос.

## Решение

Одна `SECURITY DEFINER STABLE` функция `public.get_my_pending_invites()` (миграция 0044), которая возвращает вызывающему **его собственные** pending-приглашения, уже дополненные названием пространства и публичным минимумом профиля пригласившего. Образец — `get_workspace_member_profiles` (ADR 0031):

- **Гейт — по строке приглашения:** `i.target_user_id = auth.uid()`. У функции **нет параметров вообще**, поэтому подставить чужой инвайт или чужое пространство нечем.
- **Состав выдачи — только то, что и так станет видно после принятия:** имя пространства + `public_user_id` / `nickname` / `avatar_variant` / `avatar_color` / `bio` пригласившего. Email и прочие приватные поля `profiles` не возвращаются; это закреплено pgTAP-проверкой сигнатуры.
- **Гранты по ADR 0002:** `revoke execute … from anon, public` + `grant execute … to authenticated`.
- **Только чтение.** Мутации приглашений по-прежнему идут исключительно через `accept_invite` / `reject_invite` / `cancel_invite` из 0032; членство, sync-цикл и RLS не тронуты.
- **Фильтр строк тот же, что был у клиентского SELECT** (`target_user_id = я`, `status = 'pending'`, свежие сверху) — список приглашений не меняется, меняется только состав колонок.
- **`left join`** на `sync_workspaces` и `profiles` — защитный: сейчас строка пространства пропасть не может (FK `ON DELETE CASCADE` удалил бы и приглашение, а удаление пространства в продукте мягкое), но с `inner join` любая будущая рассинхронизация молча выкинула бы приглашение из списка.

На клиенте `listMyPendingInvites()` переключён на эту RPC, а прежний прямой SELECT остаётся **fallback'ом**: если RPC на сервере ещё нет (клиент обновился раньше, чем применена миграция — по ADR 0027 это отдельное ручное действие) или она недоступна, список приглашений продолжает работать, просто без имени пространства и профиля — ровно как до этого изменения.

В UI карточка получает название пространства как заголовок и строку «От: <аватар> <ник или TF-id>»; клик по ней открывает **ту же** `MemberInfoModal`, что и список участников (ADR 0031) — отдельного экрана профиля не заводим.

## Последствия

- Приглашённый видит, куда и кто его зовёт, до принятия. TF-id пригласившего доступен из карточки — можно сверить, что это ожидаемый человек.
- Появляется первая RPC, которая отдаёт публичный профиль **не**-сопространственника. Гейт узкий (только пригласивший, только пока инвайт в `pending`), но при расширении выдачи это надо помнить.
- Требуется ручное применение миграции 0044 на прод **до** мержа клиента (ADR 0027). Fallback снижает цену ошибки в порядке выката, но не отменяет требование.
- Прежнее решение «approach 5.b» из `wave-b-plan.md` §4.4-факт остаётся в истории как есть — этот ADR его заменяет, задним числом документ не правится.
