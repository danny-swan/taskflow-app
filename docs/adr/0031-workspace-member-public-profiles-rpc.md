# ADR 0031. Публичные профили участников пространства через SECURITY DEFINER RPC (F40)

- **Статус:** accepted
- **Дата:** 03.08.2026
- **Ветка:** `feat/member-profiles-account-redesign`
- **Контекст находок:** roadmap §7.35 (F40)
- **Связанные решения:** ADR 0002 (паттерн GRANT/REVOKE для SECURITY DEFINER RPC), ADR 0006 (`get_admin_users_summary`), ADR 0008/0009/0011 (членство, реактивация, pull-матчинг членства — **не изменяются**), Post-v1.0.2 (модель идентификаторов `profiles.id` / `public_user_id`), ADR 0032 (цвет аватара, едет тем же PR)

## Контекст

Пункт 5 брифа: во «Настройки → Участники» вместо имени участника показывался «кусок цифр», а аватары у всех выглядели одинаковыми.

**Корень (доказан на проде, а не по коду).** В `MembersTab` имя строилось как `m.user_id.slice(0, 8)` — первые 8 символов внутреннего uuid. Это не «недоделанный UI», а следствие политики доступа: на таблице `profiles` есть только own-row политики `profiles_select_own` и `profiles_update_own` с условием `auth.uid() = id`. То есть клиент **физически не может** прочитать `nickname` / `public_user_id` / `avatar_variant` другого пользователя — SELECT по чужому uuid возвращает 0 строк. По той же причине аватар рисовался вариантом по умолчанию (`variant=1`) для всех, кроме тех, кто прямо сейчас онлайн: у онлайн-участников данные приходили не из `profiles`, а из presence-meta (`src/lib/presence.ts`).

Проверено SQL-запросом по проду: список функций содержал `find_user_by_public_id(p_pid text)` (миграция 0028) — прямой прецедент выдачи публичного минимума (`id`, `nickname`, `avatar_variant`) по TF-id. Функции для обратной задачи (по членству → профили) не существовало.

Ослаблять RLS на `profiles` (например политикой «видно всем участникам моих ws») нельзя: политика на таблице открыла бы **все** колонки строки, включая `email`.

## Решение

### 1. Серверная RPC вместо новой RLS-политики (миграция 0043)

`public.get_workspace_member_profiles(p_workspace_id text)` — `SECURITY DEFINER`, `stable`, `set search_path = public, pg_catalog`; join `sync_workspace_members` × `profiles`. Возвращает строго публичный минимум:

`(user_id uuid, public_user_id text, nickname text, avatar_variant smallint, avatar_color text, bio text)`

Гейты внутри функции:

- `auth.uid() is not null` — анонимам ничего;
- `has_workspace_role(p_workspace_id, auth.uid(), 'viewer')` (существующая функция из 0027) — **вызывающий сам должен быть участником** этого пространства;
- `deleted_at is null` — вышедшие участники (soft delete, ADR 0008) не отдаются.

Гранты по паттерну ADR 0002: `revoke all from public, anon`, `grant execute to authenticated`. `email` в сигнатуре отсутствует физически — это фиксируется pgTAP-кейсом, а не только код-ревью.

### 2. Клиент: тонкий слой + кэш (`src/lib/memberProfiles.ts`)

- `fetchWorkspaceMemberProfiles(wsId)` — вызов RPC, нормализация строк (`normalizeMemberProfileRow`: строки без `user_id`/`public_user_id` отбрасываются, битый `avatar_variant` → 1);
- `useWorkspaceMemberProfiles(wsId)` — хук: результат мержится в кэш `localStorage['tf.memberProfiles.v1']` и отдаётся картой `user_id → профиль`. Ошибка RPC (офлайн, local-only пространство) **не ломает UI**: остаётся то, что было в кэше;
- `memberDisplayName(profile)` — единственное место правила «есть ник → ник, иначе TF-id»;
- `lookupCachedMemberProfile(userId)` — синхронный доступ к кэшу для строк журнала активности (с in-memory зеркалом, чтобы не парсить JSON на каждый рендер).

### 3. UI

- `MembersTab`: имя = «вы» / ник / TF-id / нейтральное `ws_members_unknown` («Участник»). **Кусок uuid не выводится нигде.** Аватар — реальные `avatar_variant` + `avatar_color` участника. Имя стало кнопкой, открывающей карточку.
- `MemberInfoModal` (новый) — карточка участника: аватар, ник (или TF-id), роль в пространстве (из локального зеркала членства), «о себе», TF-id. Email не показывается, внутренний uuid — тоже.
- `ActivityEntry`: порядок резолва автора стал «я → presence → кэш публичных профилей → «Участник»». Прежний фолбэк `record.userId.slice(0, 8)` удалён.
- `presence.ts`: в meta добавлено поле `avatar_color` (см. ADR 0032), поле опционально — meta от клиента прошлой версии просто не содержит цвета и трактуется как «цвет не задан».

## Что НЕ затронуто (осознанно)

- **Логика членства и приглашений** (ADR 0008/0009/0011, `accept_invite`, `has_workspace_role`, RLS `sync_workspace_members`) — не изменена ни на сервере, ни на клиенте: новая функция только читает.
- **Sync-цикл** — `profiles` в него не входит (см. Post-v1.0.2 в roadmap), поэтому outbox/push/pull/mappers не тронуты.
- **RLS на `profiles`** — политики остались own-row; чужие профили доступны только через явную RPC с проверкой членства.

## Альтернативы

- **Новая RLS-политика «участники моих ws видят мой профиль».** Отклонено: политика даёт доступ к строке целиком, включая `email`; сузить до колонок можно только отдельным GRANT-ом на колонки, что даёт вторую, легко расходящуюся с политикой точку правды.
- **View с `security_invoker=on`.** Отклонено по той же причине: view поверх `profiles` под invoker'ом упирается в те же own-row политики и вернёт только свою строку.
- **Раздавать профили только через presence.** Отклонено — это и есть текущее поведение: офлайн-участник остаётся без имени, а история изменений (действия прошлых дней) не резолвится в принципе.
- **Класть ник/аватар в `sync_workspace_members` при accept_invite.** Отклонено: денормализация с обязательной инвалидацией при каждой смене ника, плюс правка функции `accept_invite`, к которой относятся ADR 0009/0011 — как раз тот слой, который бриф просил не трогать.

## Верификация

- pgTAP `supabase/tests/21_member_profiles_test.sql`, `plan(13)`: наличие/nullable колонки `avatar_color`, гранты (`anon` — нет, `authenticated` — да), `prosecdef`, отсутствие `email` в сигнатуре, CHECK-формат цвета, участник видит двух живых участников с их TF-id/ником/цветом, вышедший (`deleted_at`) исключён, не-участник получает 0 строк.
- vitest: `src/lib/memberProfiles.test.ts` (нормализация, аргументы RPC, ошибки, кэш, `memberDisplayName`), `src/components/MemberInfoModal.test.tsx`, обновлённые `MembersTab.test.tsx` (ник → TF-id → «Участник», аватар с цветом, открытие карточки), `TaskActivityLog.test.tsx` (uuid в разметке отсутствует).
- `npx tsc --noEmit` — чисто.
- **Прод-проба под ROLLBACK** (03.08.2026): миграции применены в транзакции, вызов от имени участника с ролью viewer вернул профили обоих участников пространства (включая явный цвет), вызов от имени не-участника — 0 строк; транзакция откачена.

## Последствия

- В UI появился публичный минимум профиля других людей — ровно тот же набор, что уже отдавала `find_user_by_public_id` (0028) при поиске по TF-id. Email по-прежнему не покидает сервер.
- Список участников теперь зависит от сети при первом открытии; при офлайне работает по кэшу, при пустом кэше показывает «Участник» вместо имени (деградация, а не ошибка).
