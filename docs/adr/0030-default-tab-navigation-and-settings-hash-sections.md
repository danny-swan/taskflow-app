# ADR 0030. Единая точка навигации на «вкладку по умолчанию» + секции «Настроек» через хэш маршрута (F38, F39)

- **Статус:** accepted
- **Дата:** 03.08.2026
- **Ветка:** `fix/f38-f39-navigation`
- **Контекст находок:** roadmap §7.33 (F38), §7.34 (F39)
- **Связанные решения:** ADR 0021–0026 (пространства), ADR 0014 (локальный слот free), ADR 0029 (очередь нативных записей)

## Контекст

Пункты 3 и 9 брифа — четыре симптома, у которых один общий слой (роутинг + инициализация активной вкладки), поэтому разбираются вместе:

1. при переключении пространства пользователь остаётся на текущей вкладке, а ожидается «Вкладка по умолчанию» из настроек;
2. иногда при входе в аккаунт пользователь оказывается во «Настройках», а не на «Задачах»;
3. клик по trial-баннеру должен вести в «Настройки → Подписка»;
4. клик по «Доступно обновление… Открыть» должен вести в «Настройки → Обновления».

### Ключевой факт: приложение работает под HashRouter

`src/main.tsx` монтирует `<HashRouter>`, то есть **весь маршрут живёт в `window.location.hash`**. Из этого вытекают сразу три из четырёх симптомов.

**Симптомы 3 и 4 — сравнение с чужим значением.** `Settings.tsx` определял целевую секцию так:

```ts
if (typeof window !== 'undefined' && window.location.hash === '#subscription') return 'subscription';
```

Но после `navigate('/settings#subscription')` реальный адрес — `#/settings#subscription`, поэтому `window.location.hash` равен `'#/settings#subscription'` и **никогда** не равен `'#subscription'`. Условие не выполнялось ни разу: все три вызывающих места (trial-баннер в `Sidebar.tsx`, две кнопки в `PaywallModal.tsx`) открывали «Основные». Второй слой — слушатель `hashchange` — тоже не помогал: react-router меняет адрес через `pushState`/`replaceState`, а они событие `hashchange` не генерируют. Это зафиксировано тестом `src/lib/settingsHashRoute.test.tsx`, который печатает оба значения из живого `HashRouter`, — то есть корень доказан фактическим поведением, а не чтением кода.

Тост об обновлении вёл просто в `navigate('/settings')` — без указания секции, поэтому открывались «Основные» даже при исправном разборе хэша.

**Симптом 2 — адрес не сбрасывается при выходе.** Выход из аккаунта делается из «Настроек» (`Settings.handleSignOut`). После `signOut()` `App` рендерит `AuthScreen` **вместо** `<Routes>`, но сам маршрут остаётся `#/settings`. Вход возвращает `<Routes>` — и пользователь снова в «Настройках». Отсюда «иногда»: если выйти с «Задач», симптома нет.

**Симптом 1 — `switchWorkspace()` не трогает маршрут.** `store.switchWorkspace()` (useStore.ts) меняет `currentWorkspaceId`, персистит его в `settings`, делает `refresh()` и переподписывает realtime — навигации там нет и быть не должно (стор не знает про роутер). Точек смены пространства несколько: `WorkspaceSwitcher`, `MyInvitesSection`, `CreateWorkspaceModal`, а также автоматические ветки в `init()`/reconcile.

Побочно найдено в том же слое: `src/pages/Checkout.tsx` использовал `<a href="/settings">`. Под HashRouter это уход на несуществующий реальный путь (в Tauri — пустой экран вместо настроек).

## Решение

### 1. Один хук вместо навигации в каждом месте (F38)

Новый `src/lib/useDefaultTabNavigation.ts` — вызывается один раз в `App`:

```ts
useDefaultTabNavigation({ ready, userId, workspaceId, defaultTab, navigate });
```

- сравнивает `userId` и `workspaceId` с предыдущими значениями; при изменении любого — `navigate('/' + defaultTab, { replace: true })`;
- **на первом проходе не навигирует**: при обычном старте маршрут уже разрулен (`/` → `/<defaultTab>`), а deep-link (`taskflow://pay/success` → «Настройки → Подписка») перебивать нельзя;
- пока `ready === false` — не навигирует и не запоминает состояние: `defaultTab` до инициализации БД ещё не пользовательский;
- при `userId === null` (вышли, показан `AuthScreen`) навигация не нужна, но предыдущее значение обновляется — поэтому вход распознаётся как смена пользователя (`null → id`) и работает даже при возврате в тот же аккаунт;
- смена пользователя и смена пространства в одном проходе дают **один** переход, а не два.

Почему одной точкой, а не `navigate` в свитчере/приглашениях/создании ws: точек смены пространства уже пять, включая автоматические ветки внутри стора, — навигацию в каждой пришлось бы дублировать и она бы разъезжалась. Это тот же принцип «убрать слой, а не надстроить»: маршрут приводится в порядок там, где меняется контекст (кто вошёл + какое пространство), независимо от того, кто именно его сменил.

### 2. Секция «Настроек» — из хэша маршрута (F39)

- Новый `src/lib/settingsSections.ts`: список ключей секций + чистая функция `parseSettingsSection(hash)`. Понимает и хэш из react-router (`'#updates'`), и полный `window.location.hash` (`'#/settings#updates'`); неизвестное значение → `null` (остаётся текущая секция).
- `Settings.tsx`: источник — `useLocation().hash` (одинаково работает в HashRouter и BrowserRouter), начальное состояние и `useEffect` на изменение хэша. **Оба сломанных слоя убраны целиком** — и сравнение с `window.location.hash`, и слушатель `hashchange`; костыля поверх них нет. Ручной выбор секции в сбоку хэш не меняет, поэтому эффект его не перебивает.
- `App.tsx`: тост обновления → `navigate('/settings#updates')`; возврат с успешной оплаты (`taskflow://pay/success`) → `navigate('/settings#subscription')`.
- `Checkout.tsx`: `<a href="/settings">` → кнопка с `navigate('/settings#subscription')`.
- Trial-баннер (`Sidebar.tsx`) и `PaywallModal.tsx` не меняются: они уже вели на `/settings#subscription` — теперь этот адрес наконец работает.

## Альтернативы

- **Перейти с HashRouter на BrowserRouter.** Отклонено: под Tauri file/custom-protocol именно HashRouter надёжен, а замена роутера — риск для всех deep-link'ов ради косметики.
- **Передавать секцию через query (`/settings?section=updates`).** Отклонено: пришлось бы менять все вызывающие места, тогда как `#subscription` уже используется в трёх точках и остаётся рабочим.
- **Навигация внутри `switchWorkspace()`.** Отклонено: стор не должен знать про роутер (сломались бы юнит-тесты стора и SSR-безопасность), плюс пришлось бы прокидывать `navigate` через модуль.
- **Сброс маршрута при выходе (в `handleSignOut`).** Отклонено как единственная мера: закрывает только выход через «Настройки» и не покрывает смену аккаунта через `AccountSwitchGate`. Хук на вход покрывает все случаи одним правилом.

## Последствия

- Вход в аккаунт и смена пространства всегда открывают дефолтную вкладку; это же правило автоматически действует для приглашений и создания пространства.
- Компромисс: если пространство меняется автоматически (reconcile после pull, когда текущее ws исчезло), пользователя тоже переведёт на дефолтную вкладку. Это редкая ветка, и переход в такой ситуации предпочтительнее, чем остаться на вкладке уже несуществующего пространства.
- Любая секция настроек стала адресуемой (`/settings#<секция>`) — новые точки входа не требуют правок в `Settings.tsx`.
- Не затронуты: логика членства/приглашений (ADR 0008/0009/0011), сам `switchWorkspace()`, схема БД (миграций нет), очередь записей (ADR 0029).

## Верификация

- `src/lib/useDefaultTabNavigation.test.tsx` — 8 кейсов: первый проход молчит; смена ws → переход; `defaultTab` берётся из настроек (`dashboard`, а не хардкод `tasks`); выход и вход в тот же аккаунт → переход; вход в другой аккаунт → ровно один переход; `ready === false` не запоминает состояние; `workspaceId === null` не навигирует; повторные рендеры без изменений не навигируют.
- `src/lib/settingsSections.test.ts` — 7 кейсов на разбор хэша, включая полный `#/settings#subscription` и все ключи секций.
- `src/lib/settingsHashRoute.test.tsx` — 2 кейса на живом `HashRouter`: доказывают корень (`window.location.hash === '#/settings#subscription'` ≠ `'#subscription'`) и что `useLocation().hash` даёт секцию, в том числе при повторной навигации на уже открытой странице.
- Полный прогон: **84 файла / 685 тестов зелёные**, `tsc --noEmit` чист. Сборка — только в CI (локально OOM).
- Ручная проверка пользователем — до закрытия находок (шаги перечислены в roadmap §7.33/§7.34).
