# ADR 0033. Soft delete уходит в облако UPDATE'ом по ключу, а не PostgREST-upsert'ом (F42)

- **Статус:** accepted
- **Дата:** 03.08.2026
- **Ветка:** `fix/f42-self-leave-push`
- **Контекст находок:** roadmap §7.37 (F42)
- **Связанные решения:** ADR 0008/0009/0011 (членство и приглашения — не изменяются), ADR 0013 (outbox и push-цикл), миграция `0031` (политики self-leave на `sync_workspace_members`)

## Контекст

Симптом, о котором сообщил пользователь: аккаунт-editor вышел из общего пространства «123», у него пространство пропало — но у владельца тот же участник остался в списке «Участники», а при следующем входе editor'а пространство появилось у него снова.

Корень доказан на прод-данных, а не по коду.

**1. На сервере выход не случился вообще.** В `public.sync_workspace_members` строка `(ws_019f67531f5b750ca62574e508d2116c, TF-B68WC7)` живая: `deleted_at is null`, `updated_at = 2026-07-22`, то есть последняя запись — дата приглашения, а не дата выхода. Локальное гашение до облака не доехало ни разу.

**2. Почему не доехало.** `pushBatch` формировал для **любой** операции, включая `op='delete'`, полный payload из локальной строки и отправлял его через `supabase.from(...).upsert(rows, { onConflict })`. PostgREST-upsert — это `INSERT ... ON CONFLICT DO UPDATE`, а Postgres проверяет **INSERT-политику RLS всегда**, даже когда фактически исполняется ветка `DO UPDATE`. На `sync_workspace_members` политика `sync_workspace_members_insert_ws_role` разрешает INSERT только владельцу пространства (`has_workspace_role(..., 'owner') or owns_workspace(...)`), поэтому у editor'а гашение отбивалось.

Прод-проба под ROLLBACK от имени самого пострадавшего пользователя (`TF-B68WC7`, роль editor в этом ws), в одной транзакции:

| путь | результат |
| --- | --- |
| `INSERT ... ON CONFLICT (id) DO UPDATE SET deleted_at=…` (как делал push) | `42501 / new row violates row-level security policy for table "sync_workspace_members"` |
| `UPDATE … SET deleted_at=now() WHERE id=…` | `OK`, погашена 1 строка |

Разница объясняется политиками: гашение своей строки покрывает отдельная политика `sync_workspace_members_self_leave_update` (`USING user_id = auth.uid() AND role <> 'owner'`, `WITH CHECK … AND deleted_at IS NOT NULL`), и она работает — но только для честного UPDATE.

**3. Почему ошибка была молчаливой.** `42501` в `isPermanentError` классифицируется как permanent (справедливо — ретраить бессмысленно), поэтому строка оставалась в `sync_outbox` с `last_error` и переставала участвовать в push'е. Пользователь никакого сообщения не видел.

**4. Почему пространство возвращалось.** Фаза 1 пула тянет своё членство `full: true` на каждом старте (F14). Раз серверная строка живая, локально погашенная строка восстанавливалась при следующем входе — вместе с пространством. У владельца та же живая строка приходила проходом B (`workspace_id IN (мои ws)`), поэтому вышедший участник продолжал висеть в списке.

Важно: шапка `push.ts` **с самого начала** описывала правильное поведение — «`.update({deleted_at: now()})` (для `op='delete'` — soft delete)». Реализация разошлась с документацией, комментарий рядом с кодом это фиксировал как осознанное упрощение («для upsert и delete используем один и тот же upsert»).

## Решение

Привести реализацию к задокументированному контракту: **`op='delete'` отправляется UPDATE'ом по ключу строки**.

```ts
const SOFT_DELETE_FIELDS = ['deleted_at', 'updated_at', 'version', 'client_id'] as const;

async function softDeleteRow(cloud: string, row: any, onConflict: string): Promise<string | null> {
  const keyCols = onConflict.split(',').map(c => c.trim()).filter(Boolean);
  const patch = /* только SOFT_DELETE_FIELDS, присутствующие в payload */;
  let q = supabase.from(cloud).update(patch);
  for (const col of keyCols) q = q.eq(col, row[col]);
  …
}
```

Ключевые свойства решения:

1. **Ключ берётся из спека таблицы** — `spec.onConflict ?? 'id'`. Для `workspace_settings` это составной `workspace_id,key`, для остальных — `id`. Отдельного справочника ключей не заводим: тот же ключ уже описан для upsert'а, второй источник правды был бы лишним.
2. **Патч узкий** — только `deleted_at`, `updated_at`, `version`, `client_id`. Гашение не должно переписывать содержимое строки (роль участника, заголовок задачи), а узкий патч заодно не задевает `WITH CHECK` политик, проверяющих неизменность ключевых полей.
3. **Delete-группа идёт построчно.** Один UPDATE на строку: удалений в батче обычно единицы, зато вердикт (успех/ошибка/backoff) у каждой строки свой, без «отравляющей строки», роняющей батч.
4. **Нет строки в облаке — это успех.** UPDATE изменит 0 строк, ошибки не будет, запись уйдёт из outbox. Так и должно быть: гасить нечего, локальная строка уже помечена удалённой, а прежнее поведение (upsert создавал в облаке заранее-удалённую строку-надгробие) было побочным эффектом, а не задуманным контрактом. Порядок внутри батча (`upsert` раньше `delete`) сохранён, поэтому «создали и сразу удалили» по-прежнему отрабатывает: сначала долетит upsert, следом гашение.
5. **Отсутствие значения ключа в payload** — внятная ошибка `soft delete: payload has no key column "…"`, запрос не отправляется.

### Что НЕ меняли

- Политики RLS, миграции, серверные функции — ни одной. Прод-проба показала, что нужная политика уже есть; проблема была целиком на клиенте.
- Логику членства и приглашений (ADR 0008/0009/0011), `removeWorkspaceMember` в сторе, порядок `PUSH_ORDER`, backoff и классификацию ошибок.
- Путь `op='upsert'` — он как был батчевым upsert'ом, так и остался.

### Рассмотренные альтернативы

- **Разрешить INSERT участнику в RLS.** Отклонено: чтобы «покинуть» пространство, право на вставку строк членства не нужно, а выдача его каждому editor'у расширяет поверхность атаки (можно было бы вставить себе строку в чужое ws при знании его id).
- **Отдельная RPC `leave_workspace()`.** Отклонено как усложнение: политика self-leave уже есть и уже проверяет ровно то, что нужно. Замена «одного сломанного слоя» на новый слой поверх противоречит принципу «проще, но стабильно».
- **Чинить только `workspace_members`, оставив upsert остальным.** Отклонено: тот же INSERT-vs-UPDATE перекос выстрелит на любой таблице, где право на вставку уже́ права на правку. Общий путь дешевле и честнее.

## Последствия

- «Покинуть пространство» доезжает до сервера: строка гасится, владелец видит уход участника (проход B пула), у вышедшего пространство больше не воскресает на следующем входе.
- Старые «сгоревшие» записи в outbox (`attempt_count >= 5` с ошибкой 42501) не оживают — намеренно, чтобы не размазывать фикс на миграцию локальной очереди. После обновления достаточно выйти из пространства ещё раз.
- Гашение не создаёт строк в облаке. Если строка не была запушена ни разу, её и не будет — консистентно с тем, что удалённых строк никто не видел.
