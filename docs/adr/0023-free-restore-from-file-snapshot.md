# ADR 0023: Файловый снапшот как fallback-источник авто-restore при пустом localStorage-слоте (F30) — пересмотр альтернативы C из ADR 0014

- **Статус:** accepted
- **Дата:** 03.08.2026
- **Ветка:** `feat/workspaces`
- **Связано:** [ADR 0014](0014-free-tier-local-account-store.md) (F21, вводит localStorage-слот; альтернатива C отклоняла авто-restore файлового снимка именно из-за необходимости перезапуска) — **этот ADR явно пересматривает отказ от альтернативы C**; [ADR 0021](0021-free-slot-workspace-aware.md) (F28), [ADR 0022](0022-restore-legacy-ws-normalize.md) (F29) — оба про тот же слот, не тронуты; `src/lib/snapshots.ts` (`createSnapshot`/`restoreSnapshot`/`readRegistry`, уже существовали); `src/pages/Settings.tsx` (`handleRestoreSnapshot`/`restartAfterRestore` — переиспользуемый механизм перезапуска); roadmap §7.22 (F21), §7.25 (F30)

## Контекст

[ADR 0014](0014-free-tier-local-account-store.md) ввёл localStorage-слот (`taskflow.localstore.v1.<userId>`) как единственный источник авто-restore данных free-аккаунта при входе/переключении на устройстве. В этом же ADR (альтернатива C) авто-restore из файлового снимка (`snapshots.ts`) был explicit-отклонён: снимок считался «универсальной страховкой перед разрушающим действием, а не хранилищем аккаунта», а главным аргументом против был **обязательный перезапуск приложения в Tauri** при каждой смене аккаунта (заменить открытый `data.db` на лету технически нельзя — файл держит sql-плагин).

На практике localStorage — менее надёжный носитель, чем файл на диске: `saveLocalAccountData` может тихо провалиться (переполнение, приватный режим, WebView-профиль) и раньше это никак не логировалось (`AccountSwitchGate.tsx` отбрасывал результат `await saveLocalAccountData(...)`). Диагностика (`f30_root_cause.md`) подтвердила по коду: при входе в free-аккаунт (`AccountSwitchGate.tsx:197-201` на HEAD `24b64c4`) `loadLocalAccountData` — единственная проверка перед сидом welcome-задачи; файловый снимок `before_account_switch`, создаваемый на каждом переключении (`createSnapshot`, строка 186/228), при этом целиком игнорируется автоматическим путём и восстанавливается только вручную через Settings → Синхронизация.

**Решение согласовано с пользователем:** источником авто-восстановления сделать НАДЁЖНЫЙ файловый снимок как fallback, когда слот пуст. Цена — один перезапуск приложения (Tauri) в этом конкретном случае. Пользователь явно принял этот компромисс ради сохранности данных. Это отменяет причину, по которой альтернатива C была отклонена в ADR 0014 — перезапуск теперь признан приемлемым.

## Решение

В `AccountSwitchGate.tsx`, free-ветка (`!isProOrTrial(ent)`), порядок восстановления данных ВХОДЯЩЕГО аккаунта (`sessionUserId`) после `setBoundUserId(sessionUserId)` + `reconcilePersonalWorkspace(sessionUserId)`:

1. **localStorage-слот** (`loadLocalAccountData(sessionUserId)`) — как и раньше, первый и самый быстрый путь, без перезапуска. Обратная совместимость: если слот есть — восстанавливаемся из него, дальше ничего не делаем.
2. **Если слота нет/пуст** — ПРЕЖДЕ чем сеять welcome, ищем последний непустой файловый снимок `label==='before_account_switch'` с `boundUserId===sessionUserId` (новая функция `findLatestAccountSnapshot`, обёртка над уже существующим `readRegistry()` из `snapshots.ts`). `readRegistry()` в этой точке уже читает реестр ВХОДЯЩЕГО аккаунта — `getBoundUserId()` берёт `bound_user_id` из БД, а `setBoundUserId(sessionUserId)` вызван строго раньше (несколько строк выше по коду), так что доп. привязка по id не нужна; фильтр `boundUserId===sessionUserId` в `findLatestAccountSnapshot` — дополнительная защита (и явная гарантия того, что safety-снимок УХОДЯЩЕГО аккаунта, созданный чуть выше в этом же проходе с `boundUserId=check.boundUserId`, не будет случайно подобран).
   - «Непустой» = `taskCount > 0`, либо (если `taskCount` не записан — легаси-снимок) `size > 4096` байт (`4096` — вес пустого SQLite-файла сразу после `clearUserData()`, зарегистрированного как safety-снимок при первом входе). Пустые снимки НЕ восстанавливаются — иначе welcome-seed никогда бы не сработал для реально нового аккаунта.
   - Если снимок найден — вызывается уже существующий `restoreSnapshot(id)` (`snapshots.ts`, без изменений). В Tauri он возвращает `{needsRestart: true}` (заменяет `data.db` на диске и требует рестарта процесса); в web — `{needsRestart: false}` (применяет JSON через `applyBackup`, рестарт не нужен).
   - Если `needsRestart === true` — welcome НЕ сеется, выставляется флаг `restartAfterAutoRestore` (тот же паттерн, что `restartAfterRestore` в `Settings.tsx` → `handleRestoreSnapshot`), пользователю показывается `ConfirmDialog` с уведомлением «Восстанавливаем данные, перезапуск…» и кнопкой перезапуска, которая вызывает `invoke('restart_app')` — идентично `Settings.tsx` → `handleRestartAfterRestore`. После рестарта приложение поднимается уже с восстановленной `data.db`.
3. **Если файлового снимка тоже нет** (реально новый аккаунт) — сеется welcome, как и раньше (`ensureSeededIfEmpty` + `ensureWelcomeTaskIfNeeded`).

Дополнительно (мелкая правка, не меняющая логику): результат `saveLocalAccountData(check.boundUserId)` (сохранение слота УХОДЯЩЕГО аккаунта) теперь проверяется — при `false` пишется `logger.warn`, чтобы будущая диагностика видела молчаливый сбой сохранения слота (раньше результат отбрасывался).

## Почему это просто и надёжно, а не костыль

- **Не вводится новый механизм.** И `restoreSnapshot`, и механизм перезапуска (`invoke('restart_app')` + `ConfirmDialog`) уже существовали и использовались вручную в `Settings.tsx` — здесь они переиспользуются буквально, без дублирования логики восстановления файла.
- **Не создаётся новый слой поверх localStorage-слота.** Слот остаётся первым и приоритетным путём (обратная совместимость, ноль изменений в `localAccountStore.ts`). Файловый снапшот — честный fallback, а не дополнительный кеш поверх существующего.
- **Явная защита от зацикливания и смешивания:** фильтр `boundUserId===sessionUserId` физически не даёт восстановить снимок ЧУЖОГО (уходящего) аккаунта; фильтр «непустой» не даёт восстановить пустышку вместо приветственного сида.

## Границы

- **Pro/Trial не затронуты.** Правка целиком внутри `!isProOrTrial(ent)`-ветки — у Pro/Trial источник истины облако, эта ветка для них не выполняется вовсе.
- **Web-режим без перезапуска.** `restoreSnapshot` в web возвращает `needsRestart: false` и применяет JSON-дамп синхронно — restart-диалог не показывается, флоу идентичен обычному restore из слота (стор обновляется через `reloadAccountBinding`/`refresh`, показывается обычный тост).
- **Ротация снимков (`MAX_SNAPSHOTS=5`, `snapshots.ts`) не меняется** — авто-restore лишь читает существующий реестр, не влияет на создание/удаление снимков.

## Альтернативы — рассмотрены и отклонены

- **Оставить всё как есть (только ручной restore через Settings).** Отклонено пользователем явно: при сбое localStorage-слота (переполнение/приватный режим/WebView-специфика) данные free-аккаунта выглядят потерянными для типичного пользователя, который не пойдёт в Settings → Синхронизация сам.
- **Чинить только надёжность самого localStorage-слота** (например, добавить резервный носитель для web/Tauri). Отклонено как более сложное и не отменяющее принципиальную хрупкость webview-хранилища; файловый снимок уже существует, уже создаётся на каждом переключении и уже физически надёжнее — задействовать его как fallback дешевле, чем чинить noSQL-подобный слот.
- **Сделать файловый снимок ЕДИНСТВЕННЫМ источником restore, убрать слот вовсе.** Отклонено: слот даёт restore без перезапуска в типичном случае (успешное сохранение) — терять этот UX ради унификации нецелесообразно. Слот остаётся быстрым путём, снимок — надёжным резервом.

## Тесты

`src/components/accountSwitchRestore.test.tsx` (новый, 6 тестов, 4 обязательных сценария из брифа F30 + 2 дополнительных edge-case):

1. Слот непуст → восстановление из слота, `readRegistry`/`restoreSnapshot` не вызываются вовсе, seed не вызывается, диалог перезапуска не показывается.
2. Слот пуст + непустой `before_account_switch`-снимок для `sessionUserId` найден → `restoreSnapshot(id)` вызван, seed не вызывается, `needsRestart:true` показывает диалог перезапуска (обычный тост о восстановлении не показывается).
3. Слот пуст + снимков для `sessionUserId` нет → seed вызывается (`ensureSeededIfEmpty` + `ensureWelcomeTaskIfNeeded`), `restoreSnapshot` не вызывается.
4. Слот пуст + единственный снимок пустой (`size=4096`/`taskCount=0`) → трактуется как «нет данных», seed вызывается, `restoreSnapshot` не вызывается.
5. (доп.) Снимок УХОДЯЩЕГО аккаунта (`boundUserId!==sessionUserId`, тот же label) игнорируется — не восстанавливается вместо сида.
6. (доп.) Несколько непустых снимков для `sessionUserId` — выбирается самый свежий по `createdAt`.

Плюс обновлён существующий `src/components/AccountSwitchGate.test.tsx` (добавлены моки `readRegistry`/`restoreSnapshot` из `../lib/snapshots`, по умолчанию — пустой реестр) — все 9 существующих тестов остаются зелёными без изменения ожиданий.

Запуск: `./node_modules/.bin/vitest run src/components/AccountSwitchGate.test.tsx src/components/accountSwitchRestore.test.tsx --pool=forks --poolOptions.forks.maxForks=2` и `./node_modules/.bin/tsc --noEmit`.

## Не делать

- Не трогать `snapshots.ts` (`createSnapshot`/`restoreSnapshot`/`readRegistry`) — вся функциональность уже была реализована и протестирована (`snapshots.test.ts`, 16 тестов), в рамках F30 переиспользуется как есть.
- Не трогать `localAccountStore.ts` — слот остаётся первым источником restore без изменений контракта.
- Не изобретать новый механизм перезапуска — переиспользуется `invoke('restart_app')` + `ConfirmDialog`, тот же паттерн, что `Settings.tsx` → `handleRestoreSnapshot`/`handleRestartAfterRestore`.
- Не запускать build (известное OOM-ограничение среды) — верификация ограничена `vitest` + `tsc --noEmit`.

## Последствия

- Free-аккаунт с пустым/сбойным localStorage-слотом, но живым файловым снимком `before_account_switch`, теперь восстанавливает данные автоматически при входе — ценой одного перезапуска приложения в Tauri (в web — без перезапуска).
- Реально новый free-аккаунт (нет ни слота, ни снимка) продолжает получать welcome-seed без изменений.
- Схема БД не менялась, миграций нет — правка полностью в клиентском TypeScript-коде (`AccountSwitchGate.tsx`).
