# ADR 0027. Миграции на прод применяются ВРУЧНУЮ (CI их не применяет); мерж `feat/workspaces → main` — без изменений БД

**Статус:** accepted
**Дата:** 03.08.2026
**Ветка:** `feat/workspaces` (перед merge-PR в `main`)

## Контекст

Перед переносом волны workspaces (F21–F33, 65 коммитов / 175 файлов) из `feat/workspaces` в `main` нужно было понять, что мерж сделает с прод-базой. Действующий документ `docs/migrations.md` утверждал: «Через Supabase Management API (POST `/v1/projects/{ref}/database/query`) — так делает CI при мерже в main». Из этого следовало, что мерж запускает необратимое применение 14 миграций (0027–0040) на прод.

Проверка по фактам показала, что это утверждение **неверно**:

1. В `.github/workflows/` всего пять workflow: `build.yml`, `db-tests.yml`, `test.yml`, `supabase-ping.yml`, `generate-updater-keys.yml`. Ни в одном нет вызова Supabase Management API, секрета `SUPABASE_ACCESS_TOKEN` или `supabase db push`. Прод-БД из CI не трогается вообще.
2. `db-tests.yml` действительно накатывает `supabase/migrations/*.sql`, но на **эфемерный vanilla Postgres 15** внутри GitHub-раннера, ради pgTAP — и удаляет его вместе с job'ом.
3. `build.yml` триггерится только на теги `v*` и `workflow_dispatch`, то есть push в `main` не собирает и не выкатывает релиз.
4. Журнал `supabase_migrations.schema_migrations` прод-проекта `sejpmzrmtgcvevukggkx` уже содержит все миграции 0027–0040 (последняя — `accept_invite_upsert_membership`, 22.07.2026). Схема прода это подтверждает: `sync_workspaces`, `sync_workspace_members`, `sync_workspace_invites`, `sync_workspace_settings`, `sync_task_activity_log`, `admin_users_summary` — на месте.

Фактический рабочий процесс всё это время был другим: миграции применялись **вручную** (Management API / MCP `apply_migration` / Dashboard SQL Editor) в момент разработки соответствующего фикса, ещё до мержа кода. Прод штатно опережал `main`. Документ описывал не реальность, а намерение, которое так и не было реализовано.

## Решение

1. **Зафиксировать реальный контракт:** применение миграций на прод — всегда **явное ручное действие** с `confirm_action` перед каждым apply. CI миграции на прод не применяет и такой автоматизации заводить не планируем (для одного оператора она добавляет необратимый риск без выигрыша).
2. **Порядок:** миграция попадает в ветку → pgTAP зелёный → ручной apply на прод → верификация (SQL из `docs/migrations.md` + Security Advisor) → мерж кода. Прод опережает `main` — это штатное состояние, а не рассинхрон.
3. **Исправить `docs/migrations.md`** припиской-уточнением (не переписывая прежнюю формулировку задним числом), явно назвав старое утверждение ошибочным.
4. **Мерж `feat/workspaces → main` выполняется merge-коммитом** (не squash): 65 коммитов и история F21–F33 сохраняются, потому что на них ссылаются `docs/audit/roadmap.md` §7.x и ADR 0021–0026.
5. **Мерж не сопровождается никаким apply:** все миграции ветки уже на проде, дельта DDL к применению = 0.

## Последствия

**Положительные:**
- Риск мержа сведён к чисто кодовому: прод-БД не меняется, релиз пользователям не выкатывается (нет тега).
- Откат тривиален: `git revert -m 1 <merge-sha>` или возврат `refs/heads/main` на `667426e71bfa38dba699438ff1728001bc54b0cb`. Прод-схема совместима с обеими сторонами отката, потому что 0027–0040 уже применены.
- Документ перестал вводить в заблуждение в самом опасном месте (необратимые операции на проде).

**Отрицательные / принимаемые:**
- Ручной apply остаётся человеческим фактором: можно забыть применить миграцию или применить не в том порядке. Компенсация — обязательная строка в Приложении А `roadmap.md`, сверка `list_migrations` и Security Advisor после каждого apply.
- Прод легально опережает `main`, поэтому «состояние main» нельзя считать описанием прод-схемы. Источник истины по схеме — `docs/architecture/erd.md` + `list_migrations` на проде.

**Не затронуто:** сами миграции 0027–0040, код приложения, RLS/GRANT-контракты, процесс сборки и тегирования релизов.
