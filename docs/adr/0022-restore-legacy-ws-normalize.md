# ADR 0022: Нормализация legacy/сиротского `workspace_id` при восстановлении workspace-aware слота (F29)

- **Статус:** accepted
- **Дата:** 03.08.2026
- **Ветка:** `feat/workspaces`
- **Связано:** [ADR 0021](0021-free-slot-workspace-aware.md) (F28, слот становится workspace-aware, `resolveWsId`/`importWsId` в `applyBackup`) — этот ADR его дополняет узкой правкой, не заменяет; [ADR 0014](0014-free-tier-local-account-store.md) (слот per-account); `src/lib/sync/workspace.ts` (`computeWorkspaceId`, `reconcileLocalPlaceholder`, `dedupePersonalWorkspaces`); `src/store/workspaceScope.ts` (`filterByWorkspace`); roadmap §7.23 (F28), §7.24 (F29)

## Контекст

[ADR 0021](0021-free-slot-workspace-aware.md) (F28) сделал слот free-аккаунта workspace-aware: `applyBackup` сохраняет исходный `task.workspace_id` каждой строки (`resolveWsId`) вместо повсеместной штамповки одним `importWsId`. Это правильно устранило смешивание пространств (§7.23) — но обнажило другой, более старый рассинхрон.

Симптом (воспроизведён пользователем): после смены free-аккаунта и обратно первое личное пространство «Мои задачи» показывает **пустой список задач**, хотя счётчик в сайдбаре и статистика показывают 3 задачи. Второе пространство («new») цело и видит свои 2 задачи корректно.

## Корень (доказан по коду)

Пересечение двух фактов, оба существовавших до F28-F29:

1. **`reconcileLocalPlaceholder`** (`src/lib/sync/workspace.ts:301`) переклеивает локальный placeholder `ws_local` в детерминированный `ws_<uid>` (`computeWorkspaceId`, `src/lib/sync/workspace.ts:24`) при первой привязке базы к аккаунту. Эта переклейка — `UPDATE ... SET workspace_id=target WHERE workspace_id='ws_local'` — затрагивает только таблицы, доступные СЕЙЧАС, в момент вызова. Задачи, которые к этому моменту уже были сохранены в слоте (§7.22, F21) СО старым `workspace_id='ws_local'`, физически лежат в JSON-дампе слота, а не в живой БД — переклейка их не видит.
2. **`filterByWorkspace`** (`src/store/workspaceScope.ts:70`) — единственный путь чтения задач/статусов/тегов/шаблонов в UI — фильтрует строго: `rows.filter(r => r.workspace_id === wsId)`, где `wsId = currentWorkspaceId`. После reconcile `currentWorkspaceId` = детерминированный `ws_<uid>`. Задача с `workspace_id='ws_local'` **не равна** `ws_<uid>` → отфильтровывается, список пуст. Счётчики и статистика, в отличие от `filterByWorkspace`, не ws-scoped — поэтому видят те же строки.

Цепочка: слот сохранил задачу с `workspace_id='ws_local'` (создана до первой переклейки placeholder'а) → F28 при restore добросовестно сохраняет этот исходный `workspace_id` (`resolveWsId`, ADR 0021) → строка возвращается в БД с `workspace_id='ws_local'` → `payload.workspaces` восстановленного набора не содержит строки `ws_local` (её там никогда не было — либо она уже погашена, либо никогда не сохранялась в слот) → задача осиротела: её `workspace_id` не соответствует ни одному восстановленному пространству → `filterByWorkspace` не находит совпадения.

**До F28** старый `applyBackup` штамповал ВСЕ восстановленные строки одним `importWsId` (текущее пространство) — legacy-задачи СЛУЧАЙНО совпадали с активным ws и были видны (ценой смешивания разных пространств при наличии второго — именно это чинил F28). F28 убрал смешивание и тем самым обнажил рассинхрон, который раньше маскировался тем же самым багом.

**`reconcileLocalPlaceholder`/`dedupePersonalWorkspaces`/`filterByWorkspace` не изменены и не являются причиной** — каждый из них корректно выполняет свою узкую задачу; правка нужна там, где происходит потеря контекста — при восстановлении слота, единственном месте, где старые (legacy) и новые (восстановленные) `workspace_id` встречаются вместе.

## Решение

В `applyBackup` (`src/lib/db.ts`), **только в workspace-aware режиме** (`isWorkspaceAware`, т.е. `payload.workspaces` присутствует), нормализовать `workspace_id` строк данных (`tasks`/`statuses`/`tags`/`task_templates`) ПЕРЕД записью:

1. Построить множество валидных ws-id — `uuid` всех строк `payload.workspaces` (то, что реально восстанавливается).
2. Если исходный `workspace_id` строки **входит** в это множество — не трогать (F28-поведение, задача остаётся в своём пространстве, включая второе личное/shared).
3. Если он **не входит** (legacy `ws_local` или любой другой осиротевший id, для которого в восстановленном наборе нет соответствующей строки `workspaces`) — переназначить на **канонический personal** ws.

Канонический personal вычисляется без завязки на `userId`/`computeWorkspaceId` (в `db.ts` этой зависимости нет и не должно быть — см. «Не делать» ниже):

- Если `settings.current_workspace_id` (тот же указатель, что уже используется как `importWsId`-фолбэк) присутствует среди восстановленных `payload.workspaces` — он и есть канонический personal.
- Иначе — personal-строка (`kind='personal'`) из `payload.workspaces` с наименьшим `sort_order` (первое созданное личное пространство, «Мои задачи», всегда `sort_order=0`; второе личное, созданное вручную, имеет `sort_order>=1` и не будет выбрано).
- Если ни один вариант не дал результата (в payload нет ни одной personal-строки) — normalize для этой строки становится no-op (оставляем исходный, хотя недостижимый, `workspace_id`) — без легаси-набора нормализовать не во что.

Легаси-бэкапы (без `payload.workspaces`, `isWorkspaceAware === false`) не затрагиваются вовсе — для них поведение `applyBackup` не меняется ни на строку (всегда `importWsId`-штамповка, как и до F28/F29).

## Почему так, а не иначе (edge-кейс canonical personal)

Целевой personal id должен совпасть с тем, что станет `currentWorkspaceId` ПОСЛЕ `reconcilePersonalWorkspace` (детерминированный `ws_<uid>`). К моменту, когда `saveLocalAccountData` вызывает `buildBackup`, первое личное пространство уже было переклеено в `ws_<uid>` (реконсиль выполняется на каждом sync-цикле, задолго до следующей смены аккаунта) — поэтому именно эта строка с `sort_order=0` лежит в `payload.workspaces`, и легаси `ws_local`-задачи, назначенные на неё, окажутся в правильном месте после restore + reconcile. Второе личное пространство (`sort_order>=1`) не выбирается никогда, поэтому его собственные (не-legacy) задачи никогда не переезжают на canonical — правило (2) выше их не трогает в принципе, т.к. их `workspace_id` валиден.

## Требования простоты (соблюдены)

Правка предельно узкая: одна дополнительная проверка внутри уже существующей `resolveWsId` в `applyBackup`, без новых модулей, без новых зависимостей, без изменений в `sync/workspace.ts`, `workspaceScope.ts` или serverside. Никакого нового слоя поверх — расширение того самого механизма (`resolveWsId`), который F28 уже ввёл для этой цели.

## Альтернативы — рассмотрены и отклонены

- **Патчить `filterByWorkspace`, чтобы он «прощал» несовпадение ws_id.** Отклонено: размывает единственный чёткий инвариант UI-слоя («видно только то, что принадлежит текущему пространству») и не решает проблему для статистики/будущих ws-scoped выборок — пришлось бы дублировать прощение везде.
- **Патчить `reconcileLocalPlaceholder`, чтобы он что-то знал про слот.** Отклонено: `reconcileLocalPlaceholder` работает с ЖИВОЙ БД в момент вызова, а нужный контекст (что restore ещё не произошёл) ему недоступен и не должен быть — это тот же класс ошибки, что F22–F27 (патч не в том слое).
- **Вычислять `computeWorkspaceId(userId)` прямо в `db.ts`.** Отклонено явным требованием — `db.ts` не должен зависеть от `sync/workspace.ts` (импорт в обратную сторону, `sync/workspace.ts` уже импортирует `db.ts`, циклическая зависимость архитектурно нежелательна). Достаточно settings-указателя, который уже используется как `importWsId`-фолбэк.
- **Нормализовать `ws_local` на этапе `saveLocalAccountData` (при сохранении, а не восстановлении).** Отклонено: слот к моменту сохранения может быть создан до первого реконсиля вообще (холодный старт без сети) — надёжнее нормализовать на restore, когда уже точно известен полный восстановленный набор `payload.workspaces`.

## Тесты

`src/lib/db.f29LegacyWsNormalize.test.ts` (новый, 4 теста):

1. Legacy roundtrip — задача с `workspace_id='ws_local'` + два personal в payload (canonical с `sort_order=0`, второе с `sort_order=1`) → после `applyBackup('replace')` legacy-задача получает canonical `ws_<uid>`, задача второго пространства остаётся на своём id. Ни одна не смешана.
2. Не-legacy задачи (их `workspace_id` входит в `payload.workspaces`) не переназначаются — F28-поведение сохранено буквально.
3. Два личных пространства без legacy-строк переживают `save → load` слота — нормализация не находит, что нормализовать (no-op), задачи не перемешаны.
4. Легаси-бэкап без `payload.workspaces` (`isWorkspaceAware=false`) — нормализация не применяется вовсе, восстановленные строки получают `importWsId`, как и до F29 (обратная совместимость).

`src/lib/db.workspaceAwareBackup.test.ts` (существующий, F28) прогнан без изменений — все 4 теста зелёные, F28-инвариант («каждая строка сохраняет свой исходный `workspace_id`, если он валиден») не нарушен.

Запуск: `./node_modules/.bin/vitest run src/lib/db.f29LegacyWsNormalize.test.ts src/lib/db.workspaceAwareBackup.test.ts --pool=forks --poolOptions.forks.maxForks=2` и `./node_modules/.bin/tsc --noEmit`.

## Не делать

- Не менять `dedupePersonalWorkspaces`, `filterByWorkspace`, `reconcilePersonalWorkspace` — ни один из них не является причиной, правка в них была бы костылём поверх симптома (тот же класс ошибки, что F22–F27, см. ADR 0021).
- Не тащить в `db.ts` импорт из `sync/workspace.ts` (`computeWorkspaceId` и т.п.) — нарушило бы направление зависимостей (`sync/workspace.ts` уже импортирует `db.ts`).
- Не запускать build в рамках этой правки (известная OOM-проблема окружения) — верификация ограничена `vitest`+`tsc --noEmit`.

## Последствия

- Затрагивает исключительно восстановление workspace-aware бэкапов (сейчас — только слот free-аккаунта, `localAccountStore.ts`); легаси-бэкапы (снимки/экспорт через `snapshots.ts`/`Settings.tsx`, не передающие `workspaces` в `buildBackup`) не меняют поведение вовсе.
- Если пользователь когда-либо создавал третье личное пространство или несколько независимых legacy-осколков — все они схлопнутся в ОДНО каноническое личное (то же самое допущение, что уже было верно для legacy-набора до появления второго пространства); это осознанный компромисс: единственная альтернатива — оставить их окончательно недостижимыми в UI, что строго хуже.
- Схема БД не менялась, миграций нет — правка полностью в клиентском TypeScript-коде `db.ts`.
